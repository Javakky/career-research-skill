## 2. 横断比較表

### 2.1 文体・長さ

| サービス | 文体 | 1 案件あたりの文字数目安 | 推奨セクション数 |
|---|---|---|---|
| Findy | 散文 + 数値 (STAR フレームワーク) | 全体 3-4 ページ / 職務要約 200-400 字 | 状況→課題→実行→結果 |
| ビズリーチ | 「見出し + 箇条書き」中心 | 職務要約 3-4 行に集約 | 開始/終了/規模/フェーズ/技術 |
| doda / エン転職 | 体言止め + 箇条書き | 開発経歴 300-500 字/案件 | 期間・規模/概要/担当工程/環境/成果 |
| LinkedIn | bullet point 短文 | 3-4 bullet / position | X-by-Y-by-Z 式 |
| レバテック FL | 散文 + 数値 | 概要 50-100 + 詳細 150-200 + 自己 PR 100-150 = **300-450 字/案件** | 期間/業務/技術/成果 |
| LAPRAS / Forkwell | プロフィール自動生成 + 手書き補足 | 自由 (GitHub 連携で半自動) | Pinned Works / Badges / 言語経験年数 |
| 転職ドラフト | 散文 + 数値 (背景→課題→工夫→結果) | 1 案件あたり具体的な数値・変化を含めて厚く (300-600 字目安) | 概要 / 背景 / 使用技術 / 工夫した点 / 成果実績 / 野望欄 |
| エン転職 (詳細) | 見出し + 表 | 期間 X 年間 / メンバー数 / 概要 / 担当業務 / 環境 / 実績 | 同上 |

| | プロジェクト / プロダクト名 | 具体名 (匿名化が必要なら NDA 注記) |
| | 業界 / ドメイン | 例: 決済 / SaaS / コンテンツ / etc |
| 体制 | 職種 | 例: バックエンドエンジニア / SE / フルスタック |
| | 役割 | リーダー / メンバー / 主担当 / オーナー |
| | チーム規模 | 例: 1-10 人 / PM 1 + Eng 5 |
| | フェーズ | 要件定義 / 基本設計 / 実装 / テスト / 運用 |
| 内容 | 業務概要 | 1-2 文で背景と目的 |
| | 担当業務 | 箇条書き or 散文で具体タスク |

| 技術 | 利用技術 | 言語 / FW / DB / インフラ / CI/CD 別 |

### 2.3 数値根拠の典型パターン (汎用例)

| パターン | 具体例の型 |
|---|---|
| 性能改善 | API レスポンス速度 X ms → Y ms (-Z%) / CWV LCP の改善 |
| キャッシュ | キャッシュヒット率 X% → Y% / 容量削減 -Z% |
| スループット | N 万件を期間内で完了 / sustained X 件/秒 |
| 規模 | N commits / M files / +A/-B 行 / テストファイル数 |
| 業務時間削減 | 月次作業 X% カット / 対象チームの工数 N% 削減 |
| 売上 | 売上 X% 向上 / 単価向上 / コスト削減 N 万円 |
| カバレッジ | テストカバレッジ X% → Y% (+Zpt) |

(具体的数値は本人 PJ 適用時に埋める)

### 2.4 サービスごとに pivot させる項目

同じ PJ を異なるサービスに出す場合、 強調軸を pivot する必要がある。

| サービス | アピール pivot | 抑えるべき軸 |
|---|---|---|
| Findy | 数値根拠 / GitHub 連携 / OSS 貢献 | スキルタグ精度 / 言語経験年数 |
| ビズリーチ | 戦略的キャリア / 事業貢献 / マネジメント | コスト削減 / 部署横断 |
| doda / エン転職 | 担当工程 / 開発環境 / 規模 | 体言止めで簡潔に |
| LinkedIn | action verb / quantification / ATS キーワード | 業界キーワード (Indeed/Glassdoor から抽出) |
| レバテック FL | 自走力 / 単価逆算 / 業務委託特性 | 客先要望対応 / スケジュール管理 |
| LAPRAS / Forkwell | アウトプット (GitHub / Qiita / Zenn 連携) / Pinned Works | 言語経験年数 / 技術タグ充実 |
| 転職ドラフト | 背景 → 課題 → 工夫 → 結果 の STAR / **野望欄** で 3-5 年後を明示 / 想定年収との連動 | 言語バージョン (Python3.9 / MySQL8.0 等) まで明記 / 失敗からの学びも書く |

### 2.5 NG パターン (共通)

すべてのサービスで共通して避けるべきパターン。

| NG | 理由 |
|---|---|
| 5 ページ以上 / 案件 1,000 字超 | 採用担当者が読み切らない (Findy / ビズリーチ共通) |
| 守秘義務違反 (顧客名 / 売上明示) | NDA / 信頼性問題 (レバテック / 業務委託特に厳格) |
| 数字のない実績 | 「改善した」「効率化した」 だけは技術理解の判断不能 (全サービス) |
| 主語ぼかし (チーム成果と個人成果が混在) | 個人寄与が見えない (全サービス) |
| 一方的な主張 / 自己中心的記述 | 協調性なしと判断 (Findy 明示) |
| 推測表現 (「〜だと思います」) | 事実ベースでないと評価不能 |
| 誤字・脱字 | エンジニアは特に厳しく見られる |
| 「N 年スパンの○○の起点」 等の forward-looking 文 | (本 skill 固有 / LL20) 当該 PJ で実際に学んだことだけ書く |

## 3. 共通最小公倍数フォーマット (推奨)

複数サービスに横展開する場合の、 いずれにも貼れる「最小公倍数」 フォーマット。

```markdown
### [カテゴリ] PJ タイトル
- 期間: YYYY-MM 〜 YYYY-MM
- 業界 / ドメイン: 〇〇
- 職種: バックエンドエンジニア / SE 等
- 役割: リーダー / メンバー / 主担当
- チーム規模: N-M 人 (PM x + Eng y)
- フェーズ: 要件定義 / 設計 / 実装 / テスト / 運用 のうち担当
- 利用技術: 言語 (X) / FW (Y) / DB (Z) / インフラ (W)
- 関連: リリース URL / 技術ブログ

#### 概要 (1-2 文 / 50-100 字)
事業背景とこのプロジェクトの目的を簡潔に。

#### 課題 (1-2 文 / 50-100 字)
着手前の制約・問題点。

#### 行動 (3-4 文 / 100-200 字)
本人が取った具体的なアクションを STAR の Action として記述。
箇条書きでもよい。

#### 成果 (1-3 文 / 50-150 字、 数値必須)
定量根拠で締める。「X (指標) を Y (定量改善) by Z (手段)」。
```

合計: 250-550 字 / 案件。 Findy / レバテック / エン転職の「300-500 字」 基準に収まり、 ビズリーチ・LinkedIn にも (要約して) 持ち込める。

### 3.2 早期 PJ 向け簡略テンプレート (LL21)

学生期 / アルバイト期 / 入社初年度の PJ には STAR を強制せず、 以下の簡略テンプレを使う。

```markdown
### [<学年 / 時期>] <PJ 名>
- 期間: YYYY-MM 〜 YYYY-MM
- 役割: 個人開発 / チームメンバー (...担当) / 等
- 利用技術: ...
- 関連: <リポ URL / 一次資料パス>

#### 概要 (1-2 文)
当該 PJ の内容を簡潔に。

#### 当時学んだ新技術 (早期 PJ の核)
- <初めて触れた言語仕様 / ライブラリ / 設計パターン>

#### 技術的制約 (任意 / コードから観測できる場合)
- <当時未習得だった概念 / コードに残る痕跡>
```

設計判断 / 成果 / 学び セクションは **省略可**。 forced narrative (LL20) を入れない。

## 4. 補足

- LinkedIn は英語フォーマットなので、 別途英訳版を持つことを推奨
- LAPRAS / Forkwell は本書フォーマットに加えて、 GitHub / Qiita / Zenn の **アカウント連携設定** を必ず実施
- ハイクラス系 (ビズリーチ / doda X) は「職務要約 (200-400 字)」 を冒頭に置き、 案件詳細は補強として
- 業務委託 (レバテック) は「単価逆算で実績テーブル」 も別途用意 (時給 × 月稼働 + 成果)
- **転職ドラフト** は審査通過必須 (不通過の約 90% は「実力判断のための情報不足」)。 共通最小公倍数フォーマットに加えて **野望欄** (3-5 年後の目標) と **言語バージョン明記** (例: `Python 3.9` / `Kubernetes 1.28` / `MySQL 8.0`) を必ず追記。 "クラウドを使った" のような抽象表記は審査で落ちる
