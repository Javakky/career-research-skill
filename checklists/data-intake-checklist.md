# データ投入チェックリスト (Phase 1)

`/career-research` を実行した際、最初にユーザーへ提示する完全チェックリスト。
**全部埋める必要はない** — 持っているものだけ列挙してもらえばよい。Claude 側で「無い」も有効な回答として扱う。

ユーザーへの提示文 (そのまま貼り付けて使う):

---

統合 CV を作るには、散らばっている一次資料の **所在情報** が必要です。
**思いつく範囲で URL / リポジトリ名 / ファイルパスを 1 回のメッセージにまとめて返してください**。
無い項目は「無し」と書いてスキップして OK です。後で追加もできます。

## A. 公開アカウント (Web fetch で取得)

- [ ] GitHub username (複数アカウント運用ならすべて。例: `alice` + `alice-corp`)
  - **Claude は `gh repo list <user> --limit 100` で全公開リポを取得し、 規模感を一覧表に整理する** (LL5)
  - 軽量 PJ (1 commit / 数 KB のスニペット) も学生期レベル感の証跡として最低限把握する
- [ ] GitLab username (公開インスタンスのみ)
- [ ] X (Twitter) handle (複数なら用途別にすべて)
- [ ] Zenn ID / Qiita ID / note ID / 業務ブログ author 検索キー
- [ ] YouTube チャンネル URL (本数 / 登録者数を集計)
- [ ] Bluesky / Mastodon / その他 SNS
- [ ] 個人ブログ / ポートフォリオサイト
- [ ] 技術コミュニティでのプロフィール (Speaker Deck / connpass / Doorkeeper)

## B. ローカル git リポジトリクローン

- [ ] クローン済みリポの絶対パス (例: `~/IdeaProjects/<repo>`)
- [ ] git log 集計に使う著者名 / メールアドレス (`--author=<name>` で検索)
- [ ] 業務リポの場合、社外公開可能な集計範囲 (年別コミット数 OK / コミットメッセージ抜粋 NG など)

> **理由**: GitHub / GitLab API は古い時期の MR を取りきれないので、ローカル git log で全期間を補完する。

## C. 内部リポ / 業務リポ

- [ ] 内部 GitLab / GHE / Bitbucket の host 名
- [ ] アクセス方法 (`glab` / `glx` MCP / SSH SOCKS5 / VPN 必須 / アクセス不可)
- [ ] プロジェクトパス (例: `org/repo`)
- [ ] NDA / 社外秘の範囲指定 (どこまで CV に書いてよいか)

## D. ローカル一次資料 (`~/Downloads/` 等)

- [ ] プレゼン (`.pptx` / `.pdf` / Google Slides export)
- [ ] 議事録 / MTG メモ (`.md` / `.txt`)
- [ ] 論文ドラフト / 寄稿原稿
- [ ] 改善提案書 / 企画書 / 事業計画書
- [ ] 確定申告書 / 契約書 (収入レンジ確認用、CV には数値のみ反映)
- [ ] LINE / メッセンジャー履歴 (制作崩壊エピソード等の参照用)
- [ ] 過去の自己紹介スライド / portfolio.pptx

> **重要**: 揮発性ディレクトリ (`~/Downloads/`) のファイルは Claude が `research/career/<userid>/assets/` にコピーして保全します。元ファイルが消えても CV から追跡可能にします。

## D-2. 外部 HDD / 物理メディア (LL26)

`~/Downloads/` 以外に、 過去のデータが大量に残っているケースが多い。 持っていれば物理メディアの mount パスと、 中の主要ディレクトリのパスを共有してください。

- [ ] 外部 HDD / SSD の mount パス (例: `/Volumes/<DRIVE_NAME>/`)
- [ ] **過去の開発成果物 / 自由制作** が入っているディレクトリのパス (個人作品 / 同人作品 / ゲームジャム作品 / ハッカソン作品 等)
- [ ] **過去のプレゼン / スライド** が入っているディレクトリのパス (.pptx / .key / .pdf / 自己紹介スライド / 学内発表資料 / 登壇資料 等)
- [ ] **学校提出課題 / レポート** が入っているディレクトリのパス (もし保存していれば / レベル感参照用 / 個別 PJ 化はしない)
- [ ] **就活アーカイブ**のパス (応募書類 / インターン技術課題 / 履歴書テンプレ等)
- [ ] **創作系元データ**のパス (小説 / ADV ボツ作品 / 同人作品 / シナリオ原稿 等)
- [ ] **古いマシンからの吸い出しアーカイブ**のパス (学校期 / 前職期に使っていたマシンから保全したファイル群)

> **ディレクトリ命名は本人の流儀**: 上記カテゴリ名は本人が普段使っている命名 (英語 / 日本語 / 略称) で OK。 Claude 側で「このカテゴリのファイルはどこに置いてあるか」 を尋ねるので、 例えば `/Volumes/MyDrive/archive/college-projects/` のように本人の命名で答えてください。

> **「揮発性ディレクトリ依存禁止」 ルールは `~/Downloads/` には適用するが、 外部 HDD / 物理メディアは別軸 (アーカイブ用途として扱う)**。 必要なファイルは `<userid>/assets/` にコピーするが、 元ファイル自体は物理メディア側に置いておいて良い。

## E. MCP 経由で読みたいソース

### F-1.5. アカウント / ID 名寄せ (LL23)

本人特定の補助手がかりとして以下を整理してください。 推測で別人と判断するのを防ぐため。

- [ ] **GitHub の複数アカウント** (個人 / 業務 / 旧 / 学籍別 / etc) を全件
- [ ] **学籍番号 / 旧 ID** (`package.json` の author / `git log --author=` の値 / Notion user_id / Slack user_id と照合用)
- [ ] **メールアドレス** (個人 / 業務 / 学校 / etc / git の Committer Email に紐付くもの)
- [ ] **内部 GitLab の hostname** (origin と API hostname が異なる場合は両方 / 例: `gitlab.example.com` (clone 用) vs `api.example.com` (API 用))
- [ ] **本人の旧ハンドル / nickname** (パッケージ名 / namespace / アバター名等に使われたもの)

### F-2. 役職の正確な範囲 (推測で格上げしない / LL2)

- [ ] **「主担当」「リーダー」「主催」「マネージャー」 の正確な範囲**
  - 議事録に名前があるだけでは役職を確定できない (参加者と主催者は別)
  - 大型イベントでは「運営コアメンバー」 と「上位マネージャーロール」 は別の役職として扱う
- [ ] 「就任予定」 と「就任確定」 の区別

### F-3. 公開 / 業績ファクト

- [ ] 社外で言及できない案件名の対応表

- [ ] 重要な受賞 / 認定 / 資格 (取得日 + 主催) — **Web 裏取り対象 (LL25)**: 自己申告と公的記録の照合が必要
- [ ] 登壇歴 (時期 + イベント名 + セッション種別)
- [ ] 大会 / コンテスト戦績 (出場 + 入賞 を区別)
- [ ] 副業の時間単価 / 売上レンジ (公開可能なら)

### F-3.5. チーム PJ の役割境界 (LL30)

チーム PJ では「本人主担当」 と「他メンバー主担当 + 本人手伝い」 を案件単位で区別したい。

- [ ] **本人主担当 (単独 / 100%)** の案件名 + 担当範囲 (ファイル / モジュール / 機能)
- [ ] **本人主担当 + チーム他メンバー協力** の案件名 + 役割比率
- [ ] **他メンバー主担当 + 本人手伝い** の案件名 + 手伝った範囲 (申告ベース)
- [ ] **チーム共通資料** (本人個人作ではない) の例 (もしあれば)
- [ ] git author / `package.json` author / Notion Created-by が本人だが、 実装は他メンバーがメインだった案件

### F-4. 学生時代 (LL6 / LL7)
